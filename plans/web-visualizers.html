Draw your program's data

A debugger exists to show you your program's data. Views already turn a type's bytes into the thing it stands for. Visualizers go one step further in the web UI: a small JavaScript file draws what a value means. Examples are a chess position as a board, a framebuffer as an image, a tree as nodes and edges, or a ring buffer of samples as a plot. Anyone can write one for their own types, and a program can carry its own.

Views extract, visualizers draw.A view statement says which data a drawing needs, using the view language, which is type-checked, budgeted, and layout-correct. The JavaScript only turns plain values into shapes. It never reads memory or knows a layout.
Nothing gets out.A renderer runs in an opaque-origin worker with no network, no storage, no DOM, and a stripped global scope. It gets only the data its statement names and returns a description of shapes, which the page draws itself.
Simple to write.One .js file beside your views, one function from data to shapes, plain JS values, and a typed API with a .d.ts for editors. No build step, no framework, no imports.
Web only, never wrong.The terminal and DAP never draw. A drawing whose data cannot be read, or a renderer that fails, shows why. It never shows a partial picture as if it were whole.
Decided 2026-10-10

Decisions

Every decision is made. Each card keeps the options that were weighed, so the reasons stay with the choice.

D1

What does a renderer run as?

Decided 2026-10-10: JavaScript in a locked-down worker

This is the core trade-off between how expressive a renderer is and how safe it is.

ChosenJavaScript in a locked-down worker, returning shapesEasy to write. Full JS for layout and maths. A worker has no DOM, and the experiments show CSP plus a global allowlist closes every channel we could find in Chromium, Chrome, and Firefox.
AltJavaScript in a sandboxed iframe with a real DOMUsers could bring d3 or their own HTML. But WebRTC's STUN packets escaped a sandboxed frame with default-src 'none' in Chromium and Chrome. CSP cannot stop that.
AltShapes declared in the view language onlyNeeds no browser sandbox at all, but there are no loops worth the name and no layout maths. That is too weak for trees, graphs, or images.
AltWebAssembly renderers, like kernelsThe strongest isolation (fuel, no imports). But it is far harder to write a chess board in Zig or C for wasm than in 40 lines of JS.
D2

How does a type get a visualizer?

Decided 2026-10-10: a visualize statement

Something has to connect a type to a renderer and say what data it needs.

ChosenA visualize statement in a view or an extendThis reuses patterns, binding, budgets, sources, and views check. The inputs are view expressions, so layout stays in the view language. extend adds a drawing to any type, including one a built-in view presents.
AltThe renderer names its types itselfThat would be one file instead of two, but the JS would need the value's raw layout. It would duplicate pattern matching and could not be checked against debug information.
D3

What does a renderer produce?

Decided 2026-10-10: shapes plus pixel images

Whatever a renderer returns crosses into the page, so the page must be able to trust it.

ChosenA picture of shapes, plus pixel imagesShapes are rects, circles, lines, paths, text, and groups. The page validates them and draws SVG, so they are crisp, themeable, accessible, clickable, and testable from the DOM. Images (RGBA pixels or an OffscreenCanvas) cover heatmaps and framebuffers.
AltA canvas onlySimplest to specify, but it is just pixels: no hover text, no clicking a square to see its value, no light/dark tokens, and tests must compare pixels.
AltSanitized HTML/SVG markupThe most expressive, but a sanitizer is a large attack surface. A typed shape list needs only a small validator.
D4

Where do drawings appear?

Decided 2026-10-10: a center Drawings view

The goal is that you see the board whenever a board is in scope.

ChosenA Drawings view in the center, beside Source, Disassembly, and MemoryIt draws every argument and local of the focused frame that has a visualizer, plus any value you pin from the value tree or a watch. It has room for a real picture, and its count badge tells you when one is available.
AltInline under the value's row in VariablesCloser to the value, but the right column is narrow (~270 px) and a board there is too small to read. It could be added later as a thumbnail that opens the view.
D5

Do renderers a program carries run without asking?

Decided 2026-10-10: yes, like views

Debugging an untrusted binary would then run its JS in your browser, inside the sandbox.

ChosenYes, like views (views plan D3)The sandbox is the protection, and it is the same for every source. Each card names the renderer's source (built-in, session, project, user, or the module that carries it).
AltAsk once per moduleThis is defense in depth against a sandbox escape, at the cost of a prompt every time you debug your own program, which is the common case.
D6

Which built-in visualizers ship first?

Decided 2026-10-10: ten built-ins, each with a test

Built-ins are generic charts that any visualize statement can name, or Draw as… applies to a value directly.

Chosenline-plot, bar-chart (horizontal and vertical), scatter-plot, histogram, box-plot (with optional error bars), donut-chart, heatmap, flame-graph, bitmap, bitsEach is specified in Built-in visualizers, function first, fast at a million points, and covered by an e2e test on a real program.
D7

JavaScript or TypeScript?

Decided 2026-10-10: JavaScript, typed by a .d.ts

Editors are better with types, and uscope must not grow a compiler.

ChosenJavaScript, typed by sdk/web/uscope-visualizer.d.ts// @ts-check gives full checking in any editor with no build step. People who prefer TS compile it to one .js themselves.
AltAccept .ts toouscope would need a TypeScript stripper (oxc or swc), a heavy dependency for a convenience.
D8

How do 3-D models get drawn?

Decided 2026-10-10: WebGL2, with a 3-D model in the e2e tests

A model you can turn needs a GPU, a canvas that stays alive between frames, and the pointer. A picture is a one-shot list of shapes. See 3-D models.

ChosenLive renderers with WebGL2, plus a built-in meshThe sandboxed worker keeps running while its card is on screen, draws each frame the page asks for into a canvas of its own, and hands it back as an ImageBitmap. It receives forwarded pointer events. Measured on a real GPU in Chrome, inside the full sandbox: 60 fps at 1280×720 with 160,000 triangles. Most people only need mesh and write no JS.
AltWebGPU as wellChromium treats the opaque-origin worker as an insecure context, so navigator.gpu does not exist there (measured). Getting it would mean serving the sandbox from a second, non-opaque loopback origin. That weakens isolation and breaks behind a proxy. WebGL2 is enough to view models.
AltSnapshots onlyPictures can already render WebGL2 into an OffscreenCanvas and return it as an image: one fixed camera, nothing to orbit. Free with D1–D3, but a model you cannot turn is a poor debugging tool.
D9

Where do built-ins run?

Decided 2026-10-10: the public API, strictly, and kept simple

A built-in is the API's first and hardest user. If it needs a private path, so will yours.

ChosenPlain renderers on the public API, in the sandbox, with no workaroundsEach built-in is a JavaScript file in views/visualizers/ that runs exactly as yours does. The page never checks a renderer's name. A built-in that wants something the API lacks either does without, or the API grows for everyone. Built-ins stay simple so the API stays small: hover through title only, no zoom or search in v1, and no shared chart helpers. Measured end to end through a warm worker: a million points reach the screen in 17–50 ms (below).
AltTrusted page code, with math in a page-owned workerRicher interaction (crosshairs, zoom, search) without growing the API. But the built-ins would prove nothing about the API, and users could never write a chart as good as ours.
D10

How do many numbers travel?

Decided 2026-10-10: typed arrays, read in bulk

A chart of a million samples cannot cost a million inspections.

ChosenNumeric sequences as typed arrays, read in bulkA sequence of numbers always arrives as a typed array, its kind set by the element type. When the elements are contiguous (an array, a slice, or a view's range(n) => p[i]), it is one memory read and one binary frame.
AltOnly through bytes()No new rule, but every view author would have to spell out pointers, lengths, and element types by hand to get a fast chart.
Start to finish

An example: a chess board

A chess engine keeps its position as bitboards and a 64-entry array of squares, each empty or holding a piece. Stored, that is six u64s, two more, and 64 Option<Piece>s. This is what anyone would want to see instead:

.uscope/views/chess.views
uscope-views 1

# Draw a board in the web UI.
extend rust chess::Board {
    visualize "chess-board" {
        squares = mailbox
        turn = side_to_move
    }
}
  • extend adds the drawing to whichever view presents chess::Board, so print board in the terminal is unchanged.
  • visualize "chess-board" names the renderer, chess-board.js beside this file.
  • Each line inside is an input: a name the renderer reads and a view expression with self as the board. Inputs bind when the view does, against the program's debug information, so a misspelled member is reported by views check, not at draw time.
.uscope/views/chess-board.js
// @ts-check
// Draws a chess position: 64 squares from a1 to h8, each empty or holding a piece.

const GLYPHS = {
  White: { King: "♔", Queen: "♕", Rook: "♖", Bishop: "♗", Knight: "♘", Pawn: "♙" },
  Black: { King: "♚", Queen: "♛", Rook: "♜", Bishop: "♝", Knight: "♞", Pawn: "♟" },
};
const SIZE = 40;

uscope.draw(({ squares, turn }, { previous }) => {
  const shapes = [];
  for (let square = 0; square < 64; square++) {
    const file = square % 8;
    const rank = Math.floor(square / 8);
    const x = file * SIZE;
    const y = (7 - rank) * SIZE;
    const name = "abcdefgh"[file] + (rank + 1);
    const piece = squares[square];
    const moved = previous !== null && !uscope.same(previous.squares[square], piece);
    shapes.push(uscope.rect({
      x, y, width: SIZE, height: SIZE,
      fill: (file + rank) % 2 === 1 ? "#f0d9b5" : "#b58863",
      stroke: moved ? uscope.theme.changed : undefined,
      strokeWidth: 3,
      title: piece.variant === "Some"
        ? `${name}: ${piece.value.color.name} ${piece.value.kind.name}`
        : name,
      select: `mailbox[${square}]`,
    }));
    if (piece.variant === "Some") {
      const { color, kind } = piece.value;
      shapes.push(uscope.text({
        x: x + SIZE / 2, y: y + SIZE / 2, size: 32, anchor: "middle", baseline: "central",
        fill: "#111", text: GLYPHS[color.name][kind.name],
      }));
    }
  }
  return uscope.picture({ width: 8 * SIZE, height: 8 * SIZE, shapes, caption: `${turn.name} to move` });
});
  • The renderer gets plain JS values. squares is an array of 64 Option<Piece>s, each {variant: "Some", value: {color, kind}} or {variant: "None"}, and the enumerations are {name, value}.
  • previous is the inputs this tab drew for the same value at its previous stop, so the renderer can mark what moved.
  • title is hover text. select names a part of the value: clicking the square shows board.mailbox[21] as a row of the value tree.
  • uscope.theme.changed is the page's own "changed" color in light and dark.

What you see

In the page

  • What is drawn. The view lists, in order, every argument and local of the focused frame whose value has a visualizer, then values pinned with Draw on a value row or Draw as… on a watch. A type with several visualizers offers each one as a tab in its card. Only cards on screen draw.
  • The address bar holds it. view=drawings selects the view and each d=PATH pins one value, optionally d=PATH~NAME for a chosen visualizer. A shared link opens the same drawings (web UI rule: the URL is the tab's whole view).
  • Across stops. Cards stay in place and redraw at each new stop the tab follows. While the program runs, the last drawing stays, dimmed, and is labelled with its stop, as every pane already does.
  • Clicking a part. A shape with select opens that part of the value as a row (expandable, editable when the row is, with Watch and Memory actions) in a popover. Keyboard: Tab moves through selectable shapes in order and Enter opens one.
  • Hover. A shape's title is its tooltip and its accessible name, so a screen reader reads "e4: White Pawn".
  • When it cannot draw. The card says why and does not draw. Causes include an input that could not be read (with the expression and reason), a renderer that threw (file:line and message), one that ran out of time or returned an invalid picture (which shape and why), or a visualizer name that no source provides.
  • Reloading. The palette's Reload views rereads every view file and renderer, so editing chess-board.js and pressing Ctrl+Shift+P → Reload redraws at once. This is the authoring loop.
docs/views.md gains a section

The view statement

visualize "NAME" # one input, `value = self` visualize "NAME" { INPUT = EXPR # separated by line ends or commas, as a `record`'s members INPUT = EXPR or EXPR … # the first alternative that binds, as `let` INPUT = bytes(PTR, LEN) # LEN bytes at PTR, read at once }
  • Where. In a view or an extend, any number of times. Every visualize that binds offers its drawing, in the order the files and views give them. The file version stays uscope-views 1: an older uscope reports the unknown statement and skips only that view, as it does today for any view with an error (src/view/syntax.rs parse).
  • Inputs. Each is evaluated like a field: with self, the view's lets, and the captured arguments in scope, and through every view, so a Vec arrives as its elements and a String as text. They bind with the view, so an input that names no member makes that visualize unbound. That is reported by info view and views check, and the rest of the view still presents.
  • bytes(PTR, LEN) is the way to hand over bulk data such as pixels, samples, or a hash table's slots. It is one memory read, not a walk of LEN elements, and arrives as a Uint8Array. The renderer reinterprets it with a DataView. Charged to the budget like any read.
  • Renderer names. Resolved as kernels are. A view calls renderers from its own source first, then the built-in ones:
    • a view file's renderers are NAME.js files beside it, read with it;
    • a module's own views call renderers the module carries (record kind 3, below);
    • built-ins live in views/visualizers/NAME.js, compiled in.
  • Carried by a program. A new record kind 3 in .debug_uscope_views: a 16-bit length and the renderer's name, then its JavaScript. An older uscope already reports an unknown kind and reads on (src/view/embedded.rs). The SDKs gain USCOPE_VISUALIZER("chess-board", "views/chess-board.js"); and uscope_views::uscope_visualizer!(…).
  • Tools. views check lists every renderer with its source and fails on a visualize naming a renderer nobody provides. info view EXPR and views explain list a value's visualizers, marked web only. Neither runs JavaScript: uscope has no JS engine, so syntax errors surface in the page with file:line.
  • Never in the terminal or DAP. print, summaries, children, and DAP variables are unaffected. Visualizers add nothing to a presentation's children.

Plain values, decided by type

Data a renderer gets

The server walks each input through the values' presentations, as the value tree does, and sends a tagged encoding that the page decodes into plain JS. A value's JS type depends only on its program type, never on the value, so u64 is always a bigint, even when it is 3.

  • Never partial. If any part of any input cannot be read (unavailable, optimized out, a view problem, or the budget runs out), the renderer is not called and the card names the first such part and why. A renderer never has to tell a real 0 from a missing one.
  • How much. A drawing's inputs get their own inspection budget, bigger than a row's (see Limits). Too-large input is a problem that suggests bytes() or a narrower expression.
  • Pointers stay addresses. The walk does not follow pointers. An input that wants a pointee says *p or uses a view that presents it.

The renderer API

A renderer is one classic script that calls uscope.draw once (or uscope.live, for 3-D and other live drawings). Its function gets the inputs and a context, and returns a picture. It may be async. The only global it can use beyond the language is uscope.

uscope.draw((input, context) => Picture | Promise<Picture>) context = { previous, // the inputs drawn for this value at the tab's previous stop, or null width, // CSS pixels the card offers; a picture is scaled to fit, never cropped theme, // "light" | "dark" } uscope.picture({ width, height, shapes, caption? }) // viewBox 0 0 width height // Shapes. Each also takes the common style and interaction properties below. uscope.rect({ x, y, width, height, radius? }) uscope.circle({ x, y, r }) uscope.line({ x1, y1, x2, y2 }) uscope.polyline({ points }) // [x0, y0, x1, y1, …] uscope.polygon({ points }) uscope.path({ d }) // SVG path data, checked against its grammar uscope.text({ x, y, text, size?, weight?, family?: "sans" | "mono", anchor?, baseline? }) uscope.group({ shapes, x?, y?, scale?, rotate? }) uscope.image({ x, y, width, height, pixels, columns, rows, smooth? }) // RGBA Uint8ClampedArray uscope.image({ x, y, width, height, canvas }) // an OffscreenCanvas you drew // Common properties fill, stroke, strokeWidth, opacity, dash // colors: CSS hex/rgb()/hsl()/names, or uscope.theme.* title // hover text and accessible name select // a part of the drawn value: `member`, `[3]`, `a.b[2].c` // Helpers uscope.theme.{ink, ink2, ink3, paper, surface, line, accent, changed, good, bad} // follow light/dark uscope.theme.series // eight categorical colors, in their validated order uscope.same(a, b) // deep equality over input values, for marking what changed uscope.color.scale(t, from, to) // blend for heatmaps; t in [0, 1]
  • Errors are the author's friend. The source is evaluated with //# sourceURL=NAME.js, so both Chromium and Firefox report the renderer's own file and line. A thrown error, a rejected promise, or an invalid shape (with its index and the property at fault) is what the card shows.
  • select is a path, not an expression. Its grammar is only member names, ., and integer indices. The page appends it to the value's own path, and the server evaluates it read-only. A renderer can never make the debugger call, assign, or evaluate anything else.
  • Canvas is there when shapes are not enough. new OffscreenCanvas(w, h) and its 2-D context, Path2D, ImageData, and DOMMatrix survive the lockdown. The page receives the canvas as an ImageBitmap, which is only pixels.
  • One worker per card. A card's worker is reused from stop to stop while the card is on screen, and no two values ever share one. It may be restarted at any time, so anything that changes over time comes through previous, not globals. A fresh worker costs 7–14 ms, and 22–33 ms with the first frame load, including 1 MiB of data.
  • What the page adds to every renderer. The Table and Copy CSV of the inputs, hover over images (the pixel's column and row), and drawing big pictures on a canvas with hit-testing. A renderer never asks for these, and built-ins get nothing more.
A pixel-grid renderer (Conway's life fixture), for comparison
// @ts-check
// Draws a life board: one byte a cell, 1 for alive, row by row.
uscope.draw(({ cells, columns, generation }, { previous }) => {
  const rows = cells.length / columns;
  const pixels = new Uint8ClampedArray(cells.length * 4);
  for (let i = 0; i < cells.length; i++) {
    const born = cells[i] === 1 && previous !== null && previous.cells[i] === 0;
    const [r, g, b] = cells[i] !== 1 ? [238, 241, 245] : born ? [176, 80, 10] : [26, 34, 48];
    pixels.set([r, g, b, 255], i * 4);
  }
  return uscope.picture({
    width: columns * 6, height: rows * 6, caption: `generation ${generation}`,
    shapes: [uscope.image({ x: 0, y: 0, width: columns * 6, height: rows * 6, pixels, columns, rows })],
  });
});
D8 · live renderers

3-D models

Say you are writing a game in C++. You stop in Renderer::submit, and mesh is an engine::Mesh: a std::vector<Vertex> and a std::vector<uint32_t> of indices. Its numbers say nothing. A model you can turn says at once that the normals are flipped or a vertex flew off to infinity. You write no JavaScript for that:

.uscope/views/engine.views
uscope-views 1

# Draw meshes in 3-D with the built-in viewer.
extend c++ engine::Mesh {
    visualize "mesh" {
        vertices = bytes(&vertices[0], len(vertices) * sizeof(engine::Vertex))
        stride = sizeof(engine::Vertex)
        position = offsetof(engine::Vertex, position)
        normal = offsetof(engine::Vertex, normal)
        indices = bytes(&indices[0], len(indices) * 4)
        index_size = 4
    }
}
  • bytes() hands over each vector's storage in one read. The renderer gets the vertex bytes, the stride, and where the position and normal sit in a vertex, read from the debug information by sizeof and offsetof. It never guesses a layout.
  • mesh also takes:
    • color: the offset of 4 bytes of RGBA per vertex;
    • primitive: "triangles", "lines", or "points";
    • index_size: 2 or 4;
    • transform: 16 floats, column-major, such as the entity's model matrix;
    • up: "y" or "z".
    Normals are computed per face when normal is absent.
  • Hover shows the nearest vertex's index and position. The viewer reports what is wrong rather than drawing around it: the caption names the first non-finite position or out-of-range index.
  • The camera is kept per card across stops, so stepping through a deformation keeps your viewpoint.

Writing your own

A live renderer owns a canvas for as long as its card is on screen. Use it for a voxel world, a navmesh over its level, a skeleton's bones, a particle system, or anything else you want to move through:

uscope.live((canvas, input, context) => { const gl = canvas.getContext("webgl2"); // or "2d"; the worker's own canvas, sized to the card // … compile shaders, upload input's buffers … return { frame(time) { /* draw; uscope shows the canvas when this returns */ }, update(input, { previous }) { /* a new stop: upload; a frame follows */ }, pointer(e) { /* {type, x, y, dx, dy, buttons, wheel, shift, ctrl, alt}: only numbers and flags */ }, key(e) { /* {key, shift, ctrl, alt}, only while the canvas has focus */ }, resize(width, height) { /* device pixels; a frame follows */ }, }; }); uscope.redraw() // ask for one more frame, say after a drag uscope.animate(on) // ask for every frame while visible, for motion uscope.caption(text) // the card's caption: counts, problems, the camera uscope.hint(text) // the tooltip under the pointer uscope.select(path) // open part of the value, as a picture's `select` does (same path grammar)
  • How frames get there. The worker draws into an OffscreenCanvas of its own, sized to the card times devicePixelRatio. When frame returns, the bootstrap hands the frame to the page with transferToImageBitmap(), and the page shows it through a bitmaprenderer context. An ImageBitmap is only pixels and moves between processes without a copy. Measured in your Chrome on its GPU: 60 fps (vsync) at 1280×720 with 160,000 triangles. Headless Chromium manages the same, so CI can run it.
  • The page drives frames. The page calls frame from its own requestAnimationFrame, but only while the card is visible and only after the renderer asked with uscope.redraw(), or continuously after uscope.animate(true). A hidden tab or a card scrolled away costs nothing. This is not just tidiness. Measured in your Chrome, requestAnimationFrame never fires in a worker started by an opaque-origin frame. A canvas whose control was transferred from the page blocks the worker forever on its first draw, because the sandboxed frame runs in another process. Both work in headless Chromium, which is why they first looked fine.
  • Lifetime. The worker lives while its card is visible and the session is on the same program. Scrolling a card away, closing the view, or switching sessions terminates it. Scrolling back starts it fresh with the current inputs. A new stop calls update; it does not restart the worker.
  • Watchdog. The page pings each live worker every second. One that does not answer within 2 s is terminated, and its card says so with a Restart button. Lost WebGL contexts are reported the same way.
  • Focus. Keys reach a renderer only while its canvas has focus, and Esc always gives focus back to the page. The debugger's own keys (F5, F10, …) are never forwarded.

What it cannot see

  • GPU memory. uscope reads the process's memory. A mesh whose vertices were uploaded and freed exists only in VRAM, so it cannot be drawn. Draw the CPU copy the asset loader keeps, or a staging buffer. Persistently mapped, host-visible Vulkan or GL buffers are mapped into the process and can be read like any memory.
  • Size. A drawing may read up to 64 MiB through bytes(). That is about two million 32-byte vertices. Bytes travel as binary WebSocket frames, never as base64 JSON. Bigger models fail with the size, not a truncated mesh.
  • WebGPU. Not offered (D8). WebGL2 runs everywhere uscope's page runs with a GPU.
  • Browsers without WebGL. The card says WebGL is unavailable. Measured: headless Firefox has no WebGL at all, even on its main thread, so the 3-D e2e test runs in Chromium and Firefox tests that message instead.
Reusing every existing path

Architecture

  • Library. In src/view, the Statement::Visualize parse, BoundVisualizer (inputs as BoundFields), renderer files beside view files (src/view_files.rs, as kernels are), embedded kind 3, and built-ins. In src/model.rs, Presentation gains visualizers: Arc<[Visualizer]>, each holding an Arc<ValueChildrenReference> whose children are the named inputs. The existing value_children_with_limits pages them, so no new request kind, scheduling, or cancellation path is needed: a resume cancels a walk as it cancels any inspection.
  • Web server. Row.visualizers: Vec<String>. New requests draw {at, path, visualizer} and renderer {digest}. The walk lives in src/web/draw.rs, modelled on cli/value.rs's expanded but producing data, so the CLI and DAP never link it. protocol.gen.ts regenerates as usual.
  • Routes. /visualizer-frame is a tiny HTML page with CSP sandbox allow-scripts; default-src 'none'; script-src 'sha256-…' 'unsafe-eval'; worker-src blob:; frame-ancestors 'self'. The page's own CSP already allows a frame from 'self'. Renderers never get a URL of their own.

Security

Threat model. A renderer may be hostile, for example one carried by a binary you were sent. It must not be able to:

  • send anything anywhere (the program's data, the session link, other values);
  • control or query the debugger;
  • read the page, its storage, or other tabs;
  • run code in the page's origin;
  • make the debugger evaluate anything;
  • hang the page.

What it may do is draw a misleading picture of data you are already looking at.

  • Ordering matters. In a classic script, a renderer's top-level declarations are hoisted before any of the script runs. D6 · D9 · D10

Built-in visualizers

Ten built-ins cover the shapes a program's data most often takes. Any visualize statement can name one, and Draw as… offers the ones a value suits with no view at all. They are ordinary renderers (D9): plain JavaScript files in views/visualizers/, using only the documented API, in the same sandbox as yours. If a built-in needs something the API lacks, it does without, or the API grows for everyone. So each is also a complete example you can copy, and each file carries the few helpers it needs (ticks, number formatting) rather than the API growing them. Each one puts function first: it shows exactly what the program holds, says what it left out, and makes every number reachable.

House rules for every chart

Straight lines, honest axes.Segments join points directly; never splines or smoothing, which invent values between samples. Bars, columns, histograms, and donuts start at zero. Line and scatter axes fit the data with round ticks and say so when log.
Nothing hidden silently.Decimated lines keep each pixel column's min and max, so a one-sample spike still shows. "Other" says how many it folds and their total. NaN, ±∞, and clipped outliers are drawn where they are and counted in the caption, and a gap stays a gap.
Every number reachable.Hover gives the exact value in the program's own type (a u64 as its full integer, a float as its shortest round-trip text), through each mark's title. Table lists every input value, and Copy CSV takes them; the page provides both for every renderer. The caption states n, min, max, and mean or total.
Change is the story.Debugging is watching data change, so each chart shows what moved since the tab's previous stop: a ghost of the old line, a tick at each bar's old length, outlines on changed cells or bits. Colors follow names, never ranks, so a series keeps its hue across stops.
One axis, few hues.Never two y-scales. At most eight categorical series, in the validated order below; a ninth folds into Other. Scatter and other all-pairs forms take three. Sequential data uses one hue; signed data is diverging blue↔red around a gray zero.
Fast under stepping.Holding F10 never queues work: each card draws only the latest stop, at most once per frame, its data arrives as typed arrays in binary frames (D10), and its renderer's worker stays warm between stops. A million points reach the screen in 17–50 ms, measured below.

Fast with many points and rapid steps

  • Bulk numbers (D10). A sequence of numbers always arrives as a typed array: Float64Array, Int32Array, BigUint64Array, and so on, decided by the element type alone. It is read in one go when its elements are contiguous: an array or slice, or a view sequence of the form range(n) => p[i], which is how the built-in views present Vec, std::vector, Go slices, and Zig lists. It travels as a binary WebSocket frame, and becoming a Float64Array costs nothing (measured: 0.000 ms for 8 MB). A million f64s is one memory read and one frame, not a million inspections.
  • Latest stop wins. Each card has at most one fetch and one draw in flight. A newer stop replaces the pending one, and stops in between are skipped. A card draws at most once per animation frame, and the stop it shows is always labelled. The server already caches answers per stop and cancels inspections when the program resumes.
  • Off the page's thread. Every renderer runs in its sandboxed worker, so decimation, binning, quantiles, and layout never block a keypress. The page only validates the picture and draws it.
  • Warm workers. Each card keeps its renderer's worker while the card is on screen, reused from stop to stop rather than spawned for each draw. That saves 7–14 ms a draw, and a crash or timeout still restarts only that card.
  • Big pictures. Up to 2,000 shapes, the page draws SVG. Past that, it draws them to a canvas and hit-tests titles and select itself, so a renderer never has to choose: 10,000 titled dots take 17–20 ms of the page's time.

Out of scope for now

Later

  • Asking for more data. Paging or zooming into a large structure, such as a transposition table, would need the renderer to request inputs, which means a request channel out of the sandbox. Not until a real need shows its shape.
  • Animation across stops beyond previous, such as a history strip or scrubbing back through earlier stops.
  • Inline thumbnails in the value tree (D4 alternative).
  • Interactive input such as dragging a piece to write memory. Writes stay in the value tree, where they are explicit.
  • WebGPU, if a browser ever offers it to an opaque-origin worker, or if a second loopback origin turns out to be worth its cost (D8).
  • Scenes of many meshes, such as a level's entities each with a mesh and a transform. That needs bytes() per element of a sequence, a small extension to inputs. Also textures, which are bytes() plus a format.
  • Export a drawing as SVG or PNG, which is easy since the page owns the DOM.
  • Chart interaction such as zooming a line plot, zooming into a flame graph's frame, or searching it. Each needs the API to grow (D9), so it waits until enough renderers want the same thing, and then every renderer gets it.
