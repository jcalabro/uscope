uscope plan

Program information at the speed of the machine

uscope turns a program's debug information into one immutable model that every client shares. Today it builds that model as a graph of millions of small heap objects, on one thread, from seven passes over the input, and throws it away when the process exits. This plan rebuilds it as flat, index-based tables: built in parallel, laid out for the cache, identical in memory and on disk, and measured continuously. The goal is to load every program faster than any other debugger while doing more work than any of them.

The fix is a different shape for the data, not a faster version of the same code:

  1. One image, one buffer. Every table is an array of small fixed-size records that refer to each other by u32 index. Strings live in one pool, variable-length data in side arrays. No Arc, Box, or pointer inside the model.
  2. The bytes in memory are the bytes on disk. A header, a directory, and 64-byte aligned tables. Saving is one write; loading is one mmap and one validation pass. The same bytes can cross a socket.
  3. Ingest in parallel by compile unit and by section on a bounded pool, then merge in unit order so the image is byte-identical for any number of threads.
  4. Build each thing once. One fused walk per unit; types deduplicated across units by structure; strings interned; indexes built once, as sorted arrays.
  5. Never guess. Instrument once and feed every reader: text and JSON reports that people, scripts, and coding agents can diff, Tracy for people at a screen, and deterministic instruction and allocation benchmarks that fail when a change regresses them.
  6. Never do it twice. Images are cached by file identity, so a program uscope has seen loads in milliseconds: every re-run, every shared library, and every test fixture.
Principles

What the data-oriented talks teach, applied here

Two talks set the method: Mike Acton's Data-Oriented Design and C++ (CppCon 2014) and Andrew Kelley's Practical Data-Oriented Design (Handmade Seattle 2021), which applies it to the Zig compiler. Debuggers that load fast have converged on the same ideas: RAD Debugger's RDI format, GDB's cooked index, LLDB's manual index, LLVM's GSYM, and Sentry's SymCache.

The purpose of all programs, and all parts of those programs, is to transform data from one form to another. … If you don't understand the data you don't understand the problem.Mike Acton, CppCon 2014
Think about a struct that you have the most of in memory and think about how you can make it smaller. That's the whole trick.Andrew Kelley, Handmade Seattle 2021

What the hardware charges

An L1 read costs about 4 cycles, L2 about 12, L3 about 44, and RAM about 180. A small malloc/free costs 200–500 cycles and a kernel call over 1,000. Arithmetic is cheaper than a read from L1. In Acton's worked example, a function reading one field from each of two objects spent about ten times as long waiting on memory as computing: it used 4 of each 64 bytes it loaded, "90% waste". Packing the inputs into arrays made it about ten times faster. This machine has 48 KiB of L1d and 1 MiB of L2 per core and 64 MiB of L3: the whole of a well-encoded image for a mid-sized program fits in L3.

The rules

P1

Know the data, then shape it

Design from measured distributions, not from a model of the world. Most functions have no generics; most line rows have no discriminator; most types are duplicates; most locals have one location. "Solve for the most common case first, not the most generic." Each table's encoding cites a measured distribution.

P2

Where there is one, there are many

No API works on one function, one type, or one DIE at a time when the caller has thousands. Ingestion transforms arrays into arrays; lookups search arrays; shared libraries load as a batch.

P3

Indexes, not pointers

Records refer to each other by u32 index wrapped in a distinct type per table, the Rust form of Zig's enum(u32) handles: half the size of a pointer, no allocation, no reference count, valid on disk and across a socket. An absent reference is u32::MAX, not an Option that doubles the field.

P4

Encodings, not one enum for everything

A tag byte plus a fixed payload, with variable-length data in a side extra array, instead of an enum sized for its largest variant. Kelley cut Zig's AST from 120 to 15.6 bytes a node and ZIR from 54 to 20.3 bytes an instruction this way, for 22% and 39% less wall time. Flags fold into the tag; rare variants get their own tags.

P5

Bools and rare fields out of band

A field set on 1% of rows lives in a sparse side table keyed by row, or the rows are sorted so the flag is implied by which range a row is in. A bool in a hot record can push a hot field onto a second cache line.

P6

Split by access, not by concept

Columns that searches scan (names, start addresses) are arrays of their own; fields read together stay together in records of 16 bytes or less. Like Acton's dictionary, keep the keys contiguous and fetch the value once found.

P7

Do it once, ideally offline

Each string is interned once, each type built once, each index sorted once, and the result kept on disk so it is never computed again for the same file. "The best code is code that doesn't need to exist. Do it offline. Do it once."

P8

Every core, by default

Ingestion is written to run on all cores from the start, as RAD Debugger's converter does ("multi-core by default"), with per-worker accumulators merged afterwards as LLDB does, and no global lock on the hot path.

P9

Measure the cost before and after

"If you don't understand the cost of solving the problem, you don't understand the problem." Every change states its expected effect in instructions, allocations, bytes, or misses, and the benchmark shows whether it happened.

What it costs the test suite

The debugger, tokio, and go suites (373 tests) take 237 s of summed test time, 16.4 s of wall time on 16 test threads. Loading debug information took 191 s of it, over 3,773 loads: every test process loads its fixture, and every launch loads libc.so.6 (668 times, 14 s, for a library with no DWARF), ld-linux (766), and the vDSO (884). A tokio fixture takes 0.9–1.4 s to load under the test profile. Faster ingestion speeds these suites up roughly in proportion; a cache makes most of that time disappear.

Why

Root causes

F1

Seven walks on one thread

Every DIE of every unit is decoded in at least seven full passes: function metadata, evaluation units, the type arena's setup, two for globals, the main variable walk, and named constants, plus extra walks for Go units and random reparses through origin chains and type references. Nothing runs concurrently.

gimli's entry reader: 1.9 G of 6.3 G instructions; each full walk ≈ 169 M instructions.
F2

Every unit's copy of every type is built

rustc describes a type again in every codegen unit that uses it. The type builder gives each copy its own TypeId, builds its members and variants, renders its name, and formats an identity key. Identity strings are later parsed back (TypeName::parse, 6.8% of instructions), and the key index is built twice.

60,839 type nodes, 6,073 distinct names (10×); o3 build: 31,781 for 4,405 (7×).
F3

Strings are copied, not interned

Every name read becomes a new String and then an Arc<str>; every source location joins a new PathBuf from the comp dir, directory, and file name; from_utf8_lossy is 4.9% of instructions on its own.

538 K string and 313 K path allocations for 813 distinct files.
F4

Records are constellations

Each record owns several heap allocations through Arc<str>, Arc<[T]>, Option<Arc<…>>, Box, and maps. Reading one function or type touches several unrelated cache lines, and building the model is dominated by the allocator: __rust_alloc alone is 5.7% of instructions.

6.4 M allocations per load. TypeIdentity ≥ 5 allocations; Expression ≥ 3.
F5

Wide, padded records

Fields are sized for the worst case: u64 lines and columns, usize keys, Option wrappers that double a field, rarely set fields stored on every row. The two line tables cost 136 B per row where 12 B would do.

See the record table above.
F6

A quadratic pass for Go

visibility::after_declaration collects and sorts every line boundary of a local's function, once per local, and stores the resulting visible ranges on the local. Large Go functions have thousands of boundaries and dozens of locals.

server-go-o0: 34,245 locals, 39.2 M addresses sorted, 83% of 14.7 G instructions; the reason Go loads take ~0.9 s and up to 571 MB.
F7

Caps from building everything eagerly

Because every object is materialized as heap records, the loader guards itself with image-wide caps. MAX_DATA_OBJECTS is a hard failure, so large programs cannot be debugged at all.

uscope's own debug build fails at 262,144 data objects after 7.4 s and 3.5 GB.
F8

Linear and repeated lookups

die_reference scans every unit for each DW_FORM_ref_addr; function_index_at scans backwards without a bound; populate_record_member_declarations re-collects a record's members once per member; the separate-debug-file fallback can run the whole load twice.

Found by the survey of src/debug_info; each is small today and large on big programs.
F9

Nothing survives the process

Each session loads everything from scratch: the same fixture in every test process, libc on every launch, shared libraries one after another on the controller thread.

191 s of 237 s in three test suites; libc loaded 668 times.
F10

Owned copies cross the boundary

Replies and evaluation clone model records: StackFrame.function: Option<FunctionInfo>, Variable.type_info: Option<TypeInfo>, TypeSource::type_info() returning an owned TypeInfo. Every clone bumps several reference counts on shared cache lines.

model.rs:3582, protocol.rs:77–617, eval/types.rs:68.
F11

No way to see any of this

The flight recorder records requests and ptrace traffic, not where time goes. Each investigation so far has meant temporary eprintln! timers, Callgrind, and DHAT with a patched allocator.

This page needed three throwaway instrumentation patches and two prototypes.
F12

Unoptimized development builds

The dev profile ran the loader at opt-level 0, 7.5× slower. Fixed in d089093: just run builds with the test profile (3.8 s → 0.9 s).

Kept here so the baseline is honest about what is already done.
Design

The image: one buffer of typed tables

A loaded module's static metadata becomes an image: one 64-byte aligned byte buffer holding a header, a directory, and a fixed set of tables. Each table is a slice of one #[repr(C)] record type, reached through a typed view; nothing in the buffer is a pointer. The public ModuleImage stays the immutable, shared model the architecture describes; it becomes a cheap handle (Arc of the buffer plus the parsed directory) whose accessors return small borrowed views instead of references to heap records.

The image is a pure function of the bytes of the files it was built from and the format version. Nothing session-dependent enters it: source maps, views, settings, and load biases stay outside, as SourcePathMap and LoadedModule already do. That is what makes it cacheable and shareable.

Design

The boundary: views and ids, not owned records

ModuleImage is public API: tests, the CLI, DAP, the web server, the evaluator, views, the runtime models, and the Linux backend call about sixty accessors on it, and integration tests match on TypeKind 28 times. The redesign keeps the accessor names where they still make sense and changes what they return:

  • Views. image.function(id) returns Function<'_>, a Copy pair of image and id whose methods (name(), declaration(), instances()) read the tables. Iterators yield views. &str borrows from the pool.
  • Types as a decoded key. Like Zig's InternPool.Key, image.type_kind(id) decodes the packed encoding into a small borrowed enum for matching; the packed form stays private. Evaluation and formatting take TypeIds and views; TypeSource::type_info() stops returning an owned TypeInfo.
  • Ids across the protocol. Replies carry (ModuleImageId, FunctionId) and TypeReference instead of cloned FunctionInfo and TypeInfo; a client resolves them against the image it already holds (web and DAP cache images by module today). Where a reply must be self-contained, it carries the few rendered fields it needs.
  • One model, not two. DwarfVariableInfo's catalog, call sites, and location expressions move into the image's tables. What remains of the provider is evaluation code over tables, so the VariableInfo trait's eighteen methods operate on ids into one buffer.

This is the largest part of the change by line count, and the most mechanical. Each phase moves one family of tables, its consumers, and the replies that carry it together, so every consumer is touched once and no phase leaves two representations of the same data.

Design

Ingestion: every core, deterministic output

S0

Open

one job

Map the file, parse the ELF header and section table, find the separate debug file, compute the identity, and probe the cache. A hit ends here.

S1

Sections

parallel by section

Decompress compressed sections concurrently; read ELF symbols, dynamic symbols, PLT and GOT; index .eh_frame and .debug_frame FDEs; read .gopclntab; parse unit headers and abbreviations.

S2

Units

parallel by unit, largest first

One fused walk per unit (or sub-unit range) into a batch of unit-local tables: functions, instances, scopes, objects, raw types with structural fingerprints, line rows, call sites, globals, constants, and the references it could not resolve locally.

S3

Merge

parallel by table, ordered by unit

Prefix sums over batch sizes assign global ids in unit order. Types are hash-consed across units and confirmed by structural comparison. Cross-unit references resolve through sorted offset tables.

S4

Analyses

parallel by item

Per unique type: names and identities. Per function: prologue refinement, resume-point decoding, Go frame-pointer analysis. Per coroutine: normalization.

S5

Indexes and seal

parallel by index

Parallel sorts build every index; tables are laid out at their final offsets; the image is validated and written to the cache in the background.

Per-unit batches

Stage S2 is where today's seven walks become one. A batch is a pure function of the unit's bytes and read-only global context (sections, the unit offset table, type-unit signatures), so workers share nothing and need no locks; each keeps its own scratch arrays alive across units, as LLDB keeps one index per worker rather than per unit. A batch records its unresolved references (DW_FORM_ref_addr, abstract origins and specifications in other units, type signatures) as (global offset, slot) pairs for S3, which replaces die_reference's scan of every unit with a binary search over unit start offsets.

Big units

The tokio server's largest unit holds 19% of its DIEs, which caps per-unit parallelism near 5×. As RAD Debugger does, a unit larger than its share of the work is split at its root DIE's children, found through DW_AT_sibling where the producer emits it and a skip-scan otherwise (decoding alone runs at 19–28 ns per DIE), into ranges processed in parallel and merged in order. This is built only when a trace shows the long pole.

Types

Each batch computes a fingerprint for every type it builds, bottom up: tag, name bytes, size, encoding, and for aggregates the members' names, offsets, and member-type fingerprints. A pointer to a named aggregate hashes the target's name and kind rather than its structure, which breaks cycles. S3 groups types across units by fingerprint and keeps one per group, the first in unit order, only after a structural comparison confirms the candidates are equal. Two versions of one crate can share a type name; a hash collision must cost a duplicate, never a wrong answer. Unique types are numbered leaves first, so a type's references point to lower ids, and names and identities are computed once per unique type in S4.

The pool

One loader pool, separate from tokio's runtime and never the ptrace controller thread, sized min(available_parallelism, 16) by default and set by a [debug_info] jobs setting or USCOPE_JOBS. jobs = 1 is a supported mode: benchmarks count instructions in it, and a test asserts it produces the same bytes as any other count. Progress is reported per unit through an atomic counter, never under a lock (LLDB lost up to 55% to a progress mutex).

Memory

Batches live until their merge, so peak memory is about the batches plus the final image. The budget is peak ≤ 2× the final image; past it, S2 merges batches incrementally in unit order instead of all at the end.

Design

Persistence: the bytes are the format

Because an image is one buffer of plain records, writing it is a single write of the buffer and reading it is a single mmap followed by validation; the tables are then read in place, straight from the page cache. No serialization framework sits in between, and nothing is deserialized.

The cache

  • Where. $XDG_CACHE_HOME/uscope/images/, beside the debuginfod cache uscope already keeps, and overridden by USCOPE_CACHE_DIR. Writes are atomic: temporary file, then rename, as separate.rs's keep does today. Eviction is least-recently-used under a size cap (4 GiB by default).
  • Keys. Most of our binaries have no build-id (rustc and Zig fixtures here have none; Go and glibc do), so the key falls back to a content hash: 1 ms for the tokio server and 30 ms for a 455 MB file with xxhsum -H2 on one thread. A small index maps (dev, ino, size, mtime, ctime) to the key so an unchanged file is not hashed again. ctime cannot be set by build tools, unlike the mtime that misled LLDB's cache.
  • Trust. A cache file is untrusted input: the trailer, the directory, and every reference are validated before use, in parallel, at memory bandwidth. A file that fails is deleted and the image rebuilt, and the report says so. --no-cache and a [debug_info] cache setting turn it off.
  • Background write. A cold load returns as soon as the image is sealed; writing the file happens on the pool afterwards.

Mapping files

Cache images and the executables and debug files being ingested are memory-mapped (D3). The unsafe this needs lives in one module, src/image/map.rs, behind one owned type:

  • One type, two calls. Mapping owns a read-only, private mapping (PROT_READ, MAP_PRIVATE) made through nix::sys::mman, whose mman feature is the only new dependency surface; Drop unmaps it. Those two calls are the module's only unsafe blocks, each with a safety comment that the existing undocumented_unsafe_blocks lint enforces. Mapping hands out &[u8] borrowed from itself, so no view can outlive it; images hold it in an Arc.
  • Edge cases are explicit. An empty file is not mapped (a zero-length mmap fails) and gets an empty slice. A file whose size changes between fstat and mmap is an error. Mappings are page aligned, which satisfies the image's 64-byte alignment.
  • The safety argument. Rust requires that the bytes behind a &[u8] do not change while it lives, and a mapped file can be changed underneath us. Cache images are ours: a user-owned 0700 directory, files written whole to a temporary name and renamed into place, never written in place, and evicted by unlinking. Renaming or unlinking leaves an existing mapping reading the old inode. That covers every writer except one that deliberately writes into our cache files.
  • Input files are the weaker case. They belong to the user's build, and a tool that rewrites an executable in place, as cp over an existing file does, would change it under the mapping. A truncation reaches the debugger as SIGBUS. Two rules shrink that window to ingestion alone. An input is mapped only while it is ingested; everything needed afterwards, such as the ELF headers that load-bias and link-map code read through ExecutableSource.data today, is copied into the image. And the file's stat identity is checked again once ingestion ends; if it changed, the result is discarded and the file ingested again, so a rewritten input can never produce a silently mixed image.
  • Kernel hints. madvise with MADV_SEQUENTIAL during validation and MADV_WILLNEED on tables about to be scanned, kept only where the benchmark shows a gain.

The tests for this module are listed under testing; they ship in the same commit as the module.

What it buys

  • Re-running uscope on an unchanged program, which is most of a debugging session's restarts, costs a read and a validation.
  • libc, ld.so, and every other shared library are ingested once per machine, not once per launch.
  • The test suite warms the cache for every fixture when just build-test-programs builds them, into target/image-cache. The 191 s of loading in three suites becomes reads. Cold ingestion stays covered by the equivalence and determinism tests, which always ingest from scratch.
  • The same bytes can go over a socket: a remote uscope web page or a future remote agent could receive the tables, not just answers.
Design

Runtime: managing images during a session

  • Shared libraries load on the pool, not one after another on the controller thread. The controller hands the loader every newly mapped module at once and keeps servicing ptrace; any request that needs a module's image waits on that module explicitly, so nothing guesses with missing metadata. Attaching to a process with hundreds of libraries loads them concurrently, mostly from the cache.
  • Lookups are searches over columns. Address to instance, function, line row, symbol, or section is a binary search over a sorted [u32]; name to functions, types, or globals is a search over sorted u64 hashes followed by a string comparison. If a trace shows these searches costing cache misses, the start columns take an Eytzinger layout; nothing is changed without that trace.
  • No clones at a stop. Building a backtrace, formatting locals, and stepping read views; replies carry ids. The --timings report covers the stop path too: time from the stop to the first published snapshot, per request.
  • Memory is accounted. Each image knows its byte size per table; info modules (or a timings field) reports it, and the session's total is a budgeted number.
Design

Observability: one instrumentation pass, many readers

Two kinds of engineers will profile uscope: people, who read timelines and flame graphs, and coding agents, which read text, parse JSON, and diff numbers but cannot look at a GUI. The code is instrumented once. Every span and counter feeds several outputs from the same pass, so neither reader needs instrumentation of its own and the two never disagree.

The rule: no one-off eprintln! timers. A new phase gets a span when it is written; an investigation starts from a timings report, a text profile, or a trace; a claimed improvement shows up in just bench --compare.

M1

Instrument once

  • An in-crate profile module: span! for phases and units, count! for per-thread integer counters (DIEs, bytes, rows, units, cache hits). It is compiled into every build, debug and release.
  • Spans never go around single DIEs or rows: a tracing span costs about 40 ns with a registry, and an enabled per-iteration Tracy zone produced 134 M zones in 2 s. Hot loops bump counters that are flushed once per unit.
  • Per span it can record wall time, thread CPU time (CLOCK_THREAD_CPUTIME_ID), allocations and bytes from a counting wrapper around mimalloc that sees every thread, and peak RSS. Where the kernel allows, it also records user-mode instructions from perf-event, reporting null where it cannot.
  • Sinks are chosen at run time (--timings, the flight recorder in debug builds) or at build time (the tracy feature). Adding a sink never means touching the instrumented code.
M2

Machine-readable first

  • uscope --timings FILE writes JSON: a schema version, a summary, counters per phase, and a traceEvents array in Chrome trace format. The trace part opens unchanged in ui.perfetto.dev, and trace_processor can query it with SQL.
  • just timings FILE [FILE] prints a compact text summary of one report, or the differences between two. --threads adds per-worker busy time, the longest unit, and the critical path.
  • Reports are stable: sorted, fixed column order, at most about forty lines by default with --all for the rest, and absolute numbers alongside percentages. That makes them diffable by a script and readable in a terminal or by an agent without paging through megabytes of trace.
M3

Deterministic regressions

  • just bench ingests a pinned corpus: the golden programs, the C++, Go, Zig, and tokio fixtures, and one large program, uscope's own debug build at a pinned commit. It runs each at jobs = 1 and at jobs = N.
  • It measures instructions at jobs = 1, which are close to deterministic (a 1 M-iteration test loop read 5,000,082 instructions on both runs), so "is it faster?" becomes a comparison rather than statistics over noisy wall times. It also measures allocation counts, peak heap, image bytes per table, and median wall time with its spread.
  • just bench --compare BASE diffs against a git revision's results or a saved file. Plain just bench compares with a checked-in baseline and fails past a tolerance: instructions and allocations ±1%, bytes exact, wall time reported but not gating. A baseline update is a commit of its own, like a golden manifest.
  • It runs in seconds, so it joins just all once it is stable.
M4

Profilers as recipes

  • just profile-instructions PROGRAM: a release build with line tables under Callgrind, printed with callgrind_annotate --inclusive=yes --tree=calling and trimmed to uscope's frames. This is how the type builder and the double TypeIndex build on this page were found.
  • just profile-heap PROGRAM: a system-alloc build under DHAT, since Valgrind cannot see mimalloc, grouped by first uscope frame by count, bytes, and bytes live at peak. This promotes the script behind the allocation table on this page.
  • just profile-counters PROGRAM: perf stat over user-mode instructions, cycles, cache misses, and branch misses for one load.
  • perf and valgrind join the default dev shell; perf is missing today. Gungraun (formerly iai-callgrind) could add Callgrind benchmarks later, but its runner must match the library version exactly and is not in nixpkgs.
M5

Tracy, for people

  • The tracy Cargo feature makes every span! also a Tracy zone and every counter a plot, through tracy-client =0.18.4, the version that matches nixpkgs' Tracy 0.13.1. Tracy refuses any other client version, and tracy-client 0.19 claims to support the older client library but does not compile against it. A gate check asserts that tracy-client-sys resolves to 0.28.0.
  • Build it with default-features = false plus enable, ondemand, and only-localhost. Leave out sampling and system tracing, which open inherited perf events that would follow the debuggee. Leave out the crash handler, which installs fatal-signal handlers, and broadcast, which sends UDP announcements.
  • tracy-alloc wraps mimalloc in ProfiledAllocator to show memory per zone.
  • A nix develop .#profile shell adds tracy, samply, hotspot, heaptrack, hyperfine, poop, and KCachegrind, keeping GUI tools out of the default shell.
OpenTelemetry was considered and rejected: it is built for exporting service traces to a collector, its trace API is still beta in Rust, and it brings no timeline, plot, memory view, or CSV export. puffin is maintained sporadically and framed around game frames. The tracing ecosystem's cost (40 ns a span with a registry, 150 ns through tracing-tracy) buys nothing a small in-crate macro does not.
Decisions

Decided

Decided 2026-10-08: every recommendation below was accepted except D3, where the cache and input files are memory-mapped from the start rather than later.

D1

Viewing bytes as records

Decidedzerocopy derivesSafe transmutes checked at compile time (FromBytes, IntoBytes, KnownLayout); the in-memory type is the on-disk type; no unsafe in our code.
AltrkyvA second "archived" type for every record and a framework between us and the bytes; the point is that the live type is the archived one.
AltbytemuckSimilar, with less layout checking (Pod forbids padding rather than checking it).
D2

The worker pool

Decidedrayon, one dedicated bounded poolOrder-preserving parallel collect keeps results deterministic; parallel sorts build the name indexes (12 M entries for the large program); work stealing balances uneven units.
AltScoped std threads and an atomic work counterNo dependency, and exactly what the prototype measured, but we would write and maintain the parallel sorts and merges ourselves.
D3

Reading files: mmap

Decidedmmap from the start, for cache images and input filesZero copy: a cached image is usable as soon as it is validated, with no 120 ms read for a 455 MB file, and processes share one copy in the page cache. It costs one small module of unsafe with a written safety argument and its own tests (§ Mapping files).
Altread into an aligned bufferNo unsafe and 1.3 ms for 15 MB, but a full copy of every file and no sharing between processes.
D4

Eager or lazy

DecidedEager and complete, made fast and keptBuild everything for every unit, in parallel, and cache it. One code path, deterministic, and every query answered from tables. Answers that depend on the whole program (types, globals, coroutines) never wait on a lazy unit.
AltIndex eagerly, materialize units lazilyWhat gdb and lldb do. It is cheaper for the first load of an enormous program, but it adds a second state to every lookup and makes results depend on which units happened to be loaded. Revisit only if the large-program budget is missed.
D5

Strings

Decidedu32 offsets, NUL-terminated, .debug_str copied whole4 bytes per reference and free interning for DWARF's own strings. Length is a SIMD memchr over short names.
Alt(offset, len) spans8 bytes per reference to save a memchr.
AltIntern every string by contentA smaller pool, but hashing every string is what made GDB's and LLDB's indexers slow.
D6

Cache on by default

DecidedOn, with a size cap and --no-cacheMost of the gain for users and tests comes from the cache. Every cache file is validated, and a cold ingestion produces the same bytes as a cached one.
AltOpt-inWhat LLDB does. Few users would ever turn it on.
D7

Instrumentation

DecidedAn in-crate span!/count! feeding several sinksAbout 1.5 ns when off. Text and JSON reports for agents and scripts, Tracy zones (about 22 ns each) for people, from the same instrumentation; under our control, and compiled into release builds.
AltTracy as the primary toolExcellent for a person at a screen. An agent can reach it only through tracy-capture and tracy-csvexport, a live connection, and an exact version pin, which yields aggregates without the timeline that makes Tracy worth using.
Alttracing with subscribersAbout 40–175 ns per span, a dependency stack, and an async span model this code does not need.
D8

Cache keys

DecidedBuild-id, else XXH3-128 of the contents; stat as a fast path including ctimeFast, and it catches accidental change. Validation, not the hash, protects against a malformed file.
AltBLAKE3Cryptographic strength we do not need, at several times the cost per core.

One rule in AGENTS.md changes: "Debug-info providers normalize data at the boundary" stays, and gains "into image tables, which are a pure function of the input files". The rule against unsafe code stays, with one named exception: the mapping module of D3, whose two calls are the only unsafe this work adds.

Plan

Phases and tracking

The order is chosen to finish the whole rewrite with the least total work, not to deliver partial wins early. Four rules decide it:

  • No work on code that will be deleted. Today's loader gets no fixes, not even the Go pathology. Its replacement is built correctly the first time, and the old loader serves only as the oracle until each family is ported.
  • Infrastructure is written once, in its final form. The pool, the per-unit pipeline, the ordered merge, the file format, and the validator arrive with the first tables. No serial loader is ever written to be parallelized later.
  • Each consumer is touched once. A table family's phase does all of its work in one pass: its ingestion, its tables, every consumer, the protocol replies that carry it, and the deletion of its old types. No separate "boundary" pass revisits the same code.
  • Dependency order. Lines depend on nothing. Functions and symbols need strings and lines. Types need strings. Variables, locations, and coroutines need all three. The cache is wired once nothing of the old model remains.

The cost of this order: until P4 finishes, both loaders run, so loads and the test suite stay about as slow as today. The big test-time win arrives in P5. Each task lands in commits that keep the full gate green and records its measured result here. Status: todo doing done.

Testing

Keeping it correct while it moves

  • Equivalence. Until the old loader is deleted, every fixture is loaded by both loaders and their canonical dumps must match: functions, instances, lines, symbols, types by identity, globals, scopes, and objects. Intended differences, such as duplicate types collapsing, are normalized in the dump, never allowed through as a mismatch.
  • Determinism. Images are compared byte for byte across thread counts and across runs. The simulator's fingerprint includes each corpus image's hash, so a change that moves an id is seen at once.
  • The unsafe module. The mapping module is tested on its own, before anything depends on it:
    • a mapped file reads exactly what fs::read reads, for sizes 0, 1, a page minus one, a page, a page plus one, and a sparse file larger than 4 GiB;
    • a mapping still reads the old contents after its file is replaced by rename, and after it is unlinked, which is what eviction and atomic cache writes rely on;
    • an input rewritten during ingestion is detected by the identity check and ingested again, never returned mixed;
    • truncating a mapped file in a child process and reading past the new end raises SIGBUS in that child, documenting exactly the hazard the safety argument excludes;
    • compile_fail doc tests show that a view cannot outlive its Mapping;
    • every image test runs against both backings, mapped and an owned aligned buffer, and must agree. The owned backing also runs under Miri (just miri), which cannot execute mmap but checks every byte-to-record view and validator path for undefined behavior. The image fuzz target exercises both.
  • Untrusted input. The existing DWARF and ELF fuzz targets drive the new walk. A new target corrupts image files, and the validator must reject them without panicking. Every u32 limit has a test that it fails explicitly.
  • Behavior. The scenario suites stay the arbiter of what the debugger answers; this work changes how, not what. Lifecycle changes in P6 follow the repository's concurrency rules: cancellation, cleanup, no surviving inferiors, and just stress.
  • Resources. Tests run with images from the warmed cache and jobs set low, so sixteen concurrent test processes do not each start sixteen loader threads. The per-process 1 GiB cap stays; the allocation test counts every thread.
  • Performance. just bench in just all, with a baseline that moves only in commits of its own.

Ideas

Further out, each with what we know

I1

Reuse units across rebuilds

After a one-line edit to the tokio server, 0 of 119 units were byte-identical: relinking moves every address. With address attributes ignored, 85 units (58% of the bytes) matched, and the rest differed only in addresses embedded in location expressions. Reusing unit batches across builds would need address-relocatable batches and fingerprints that ignore addresses. This becomes interesting once cold ingestion is near its floor.

I2

Ingest before anyone asks

uscope web and DAP sessions already know the program's path. They could watch it and re-ingest in the background as soon as the build rewrites it, so the image is cached by the time the user restarts. RAD Debugger pre-converts the debug info of libraries next to the program for the same reason.

I3

Abbreviation-specialized decoding

gimli decodes each attribute generically, at 19–28 ns per DIE. Most abbreviations use only fixed-size forms, so the offsets of the attributes we want can be computed once per abbreviation and the rest skipped, as GDB decides interest per abbreviation. Measure first: it matters only once everything else is near the floor.

I4

Tables in the browser

The web page could receive the symbol and name tables as typed arrays and search them locally: fuzzy "go to function" with no round trip, from the same bytes as the cache.

I5

Huge pages and prefetch

For images of hundreds of megabytes, madvise(MADV_HUGEPAGE) on the buffer and software prefetch in index builds may cut TLB and cache misses. Apply only with counters showing those misses.

I6

Shared caches

Images are content-addressed and self-validating, so a team or CI could share a cache directory, or publish images beside a release's debug files, much as debuginfod serves debug files.
