A browser debugger you can send as a link

uscope web ./app serves a dense, keyboard-driven React app and a WebSocket from the uscope binary. Every pane is a view of one focus: a stop, a thread, a frame, a place in the code. The URL is that focus, so a link you paste to a coworker opens the same live session at the same place.

  • One live session, many viewers. Every tab connected to a uscope web process sees the same debugger, and each tab keeps its own focus.
  • Never silently wrong. A pane shows data only for the stop it read. While the program runs, old values stay on screen, dimmed and labelled with their stop.
  • Your place survives every stop. Expanded trees, scroll positions, and selections stay put when you step, and values that changed are marked.
  • Fast to change. Hot reload, a type-checked protocol, tests that run in seconds, and screenshots an agent can look at.

The mockups on this page use the colors, type, and density proposed for the app, in both themes. The example program is an illustration: a small multithreaded key-value server.

The main screen

The interface

One screen, resizable splits, no modal dialogs. The left column says where you are, the center shows the code, the right column shows what you are looking at. Switch the mockup between states to see how running and view-only access change it.

1

The address bar is the focus. Session, stop, thread, frame, then what you are looking at. Copying it shares this exact view.

2

Run state is the loudest thing on screen. Stopped, running, or not started, with the stop number every pane's data belongs to.

3

Presence. Who is connected, with what access. Hover a person to see their focus; click to go there.

4

Source, disassembly, and memory are three views of one place. Switching keeps the address. The program counter line follows in each.

5

The stopped line, with values inline. Values on lines just executed appear beside them; changed ones are marked. Hover any name to evaluate it.

6

The console runs expressions and uscope's commands, with completion from the frame's variables, members, and registers.

7

Changed since the last stop, with the old value beside it. Watches live in the URL, so a shared link brings them along.

8

Expansion survives stepping. The tree remembers paths such as args/req, not row handles, and reopens them at each stop.

9

Stop history. Every stop this session, clickable. An old stop opens with a banner, never with newer values.

How it is used

User flows

Start a session and stop somewhere

  1. Run uscope web

    $ uscope web ./build/kvstore --port 7000 debugging ./build/kvstore (not started) open http://127.0.0.1:7341/join#c-7f3a9d2e41b8 anyone with this link can control the program

    One process, one program. --attach PID and --core FILE work the same way; --open opens the browser.

  2. Open the link

    server.c · main
    Not startedF5 runs kvstore
    142 int main(int argc, char **argv) {

    The token becomes a cookie and leaves the address bar. The page opens on main (D2).

  3. Set a breakpoint

    46 e = table_insert(…);
    Click the gutter, or F9
    Shift+F9 adds a condition inline

    Breakpoints resolve against the executable before it runs, and show where they landed.

  4. Continue and stop

    Stoppedstop #10 · breakpoint 1
    /s/k7q2/stop/10/t/41872/f/0?src=server.c:46

    F5. The address bar becomes the new focus. Every pane fills in for stop #10 without waiting on the others.

Step and inspect

  1. Expand what matters

    ▾req0x7ffff7a3e010
    key"user:1042"

    Open req in Variables. The URL records x=args/req.

  2. Step twice

    ▾reqstill open
    stats.inserts17was 16

    F10 F10. The tree stays open and scrolled where it was; changed values are marked until the next stop.

  3. Watch an expression

    select c->server->stats.inserts w
    &w=c->server->stats.inserts

    Select text in the source and press w, or type in Watch. Hover evaluates without adding it.

  4. Look up the stack

    1serve_connserver.c:74
    …/stop/12/t/41872/f/1?src=server.c:74

    Click frame 1, or press u. Source, variables, and registers move to that frame. Nobody else's view moves.

Share with a coworker

  1. Click Share

    Can view
    Can control

    Share copies a join link to the current view. y copies the plain link, without access, for someone already in.

  2. They open it

    $ ssh -L 7341:127.0.0.1:7341 devbox # then open the link

    uscope only listens on localhost, so a coworker on another machine tunnels in. On a shared box, the link just works.

  3. Both of you are there

    JCRrobin joined, can view
    robin is at frame 1, serve_conn

    Each of you has your own focus. Click a person to jump to theirs.

  4. You step; they follow

    #13jc stepped over · server.c:50

    Their tab moves to the new stop (D3) and a notice says who did it. A viewer's run controls are disabled and say why.

Open a link that is out of date

  1. The stop has passed

    Stop #12 has passed. The session is at stop #15, table.c:77 in worker-1. Go to stop #15Stay on server.c:49
    values hidden: they belong to stop #12

    The file and line are still shown, since they do not change. Values are not, since they would be stop #15's under stop #12's address.

  2. The session has ended

    This session ended. uscope web on 127.0.0.1:7341 is now debugging something else, or nothing.
    link pointed at kvstore · server.c:49

    A session id from an earlier run never opens a different program.

  3. The connection drops

    Reconnectingshowing stop #12

    Panes keep their last data, dimmed. On reconnect the server sends its state and the tab resumes from the URL.

  1. Continue

Links

URLs

The path names the debugger state; the query names how you are looking at it. Together they are the focus, so the address bar is always a working link.

URLOpens
/The session, at its current stop.
/join#TOKENTrades the token for a cookie, then goes to the link's focus. The only URL that carries a secret.
/s/k7q2/liveFollows whatever the session does next.
/s/k7q2/stop/12/t/41872/f/1Stop 12, thread 41872 (kernel thread id), frame 1. A passed stop shows a banner.
…?src=server.c:46-49The file shown and the lines selected.
…&asm=0x555555555a3cDisassembly at an address.
…&mem=0x7ffff7a3e020Memory at an address.
…&w=c->server->stats.inserts,req->keyWatch expressions.
…&x=args/req,locals/e/nextExpanded paths in the variable tree.
  • Session ids are random and minted when uscope web starts, so a link from an earlier run says the session ended rather than opening something else.
  • Stop numbers are uscope's own StopIds, which the debugger already checks on every request.
  • Following a new stop replaces the address rather than pushing history, so Back leaves the debugger instead of walking through every step. The stop strip is the history.
How it fits together

Architecture

  • Our own protocol on DebuggerHandle, not DAP. DAP has one client per session, and its session owns and ends its debugger. The handle already clones, broadcasts events, publishes revisioned snapshots, and makes racing clients fail by StopId. A custom protocol also keeps structure DAP flattens to strings, such as disassembly tokens and typed values.
  • Never the shared selection. The controller keeps one selected thread and frame, which CLI commands and DAP's console change. Every web request names its stop, thread, and frame through DebuggerHandle::at, so tabs never move each other.
  • Share presentation, don't copy it. Values and frames are formatted by the library and cli::format, as DAP does. Pieces that live only in DAP's session (frame naming, scopes, completion, disassembly padding) move to shared functions first, in changes of their own, with DAP's tests unchanged.
  • The session owns program I/O. Output goes through pipes to every tab, with a bounded ring so a late joiner sees recent output. Input comes from the console's input mode.
  • Source contents are a new library request. read_source(SourceFileId) reads only files the debug information names, through the source map, off the controller thread.
  • Node never touches cargo build. just web builds into build/web; a small build.rs embeds whatever is there, or nothing, in which case the page says to run just web.
On the wire

Protocol

State is pushed; data is pulled. On connect the server sends hello and the full state; at each new revision it sends state again, coalesced so a burst sends only the newest. Everything else is a request that names its stop.

// server → every tab, at each revision {"event": "state", "revision": 88, "inferior": {"stopped": {"stop": 12, "thread": 41872, "reason": {"step": "over"}}}, "threads": [{"id": 41872, "name": "worker-2", "stopped": true}, …], "breakpoints": [{"id": 1, "spec": "server.c:46", "hits": 3, …}], "watchpoints": []} // server → every tab {"event": "notice", "who": "jc", "did": "stepOver", "stop": 13} {"event": "output", "stream": "stdout", "text": "listening on :7000\n"}
// tab → server {"id": 7, "method": "scopes", "params": {"stop": 12, "thread": 41872, "frame": 0}} // server → that tab {"id": 7, "result": [{"name": "Arguments", "rows": [ {"name": "req", "type": "struct request *", "summary": "0x7ffff7a3e010", "children": 31, "path": "args/req", "evaluateName": "req"}]}]} // a request for a stop that has passed {"id": 9, "error": {"kind": "staleStop", "message": "stop 12 is no longer current"}}
  • Requests: backtrace, scopes, children, evaluate, complete, console, disassemble, readMemory, registers, source, breakpointLines, modules, and the changes: continue, step, pause, kill, restart, breakpoints, watchpoints, setVariable, writeMemory, signal policy.
  • Errors are a closed set the UI handles: staleStop, notStopped, forbidden, invalid, unsupported, failed, each with the debugger's message.
  • Value handles (children: 31) belong to one connection and one stop, and fail as stale afterwards. The UI keys expansion by path and re-opens the same paths at the next stop. "Changed" compares summaries at the same path.
  • Types are Rust structs in src/web/protocol.rs. A test generates web/src/protocol.gen.ts with ts-rs and fails if the checked-in file differs, so the two sides cannot drift.
  • Lag: if a connection falls behind the event stream, it gets a fresh state, the recovery DAP already uses.
Access

Security

The socket can do anything a debugger can, including running code inside the program. So:

  • Localhost by default. --listen ADDRESS exposes it on purpose; the docs recommend an SSH tunnel instead.
  • A token per run, per role. The join link's token is traded for an HttpOnly, SameSite=Strict cookie and removed from the address bar, so ordinary copied links carry no secret. Control and view tokens differ; a viewer's changes fail with forbidden.
  • Host and Origin checks. Host must name the server (which stops DNS rebinding) and Origin must be its own. The DAP server's rule of refusing any browser stays as it is: different endpoint, different policy.
  • Nothing else is served. Assets, /join, and /api/ws. No CORS. Source reads are limited to files the debug information names.

Confidence

Testing

Each layer tests what only it can, in seconds, and every one uses the real server or the real browser.

Server scenarios

Rust tests start uscope web on a fixture and drive it with real WebSocket clients: tokens, roles, Host and Origin; two tabs continuing at once (one wins, one gets staleStop); stale handles; lag; a late joiner's output; disconnecting while running; shutdown leaving no inferior behind.

nextest · seconds
Recorded transcripts

Those scenarios save their traffic. Vitest replays it into the real store, so the UI's state logic is tested against what the real server says, with no hand-written mock server. A transcript that no longer matches the generated types fails.

vitest · <1 s
Components

Vitest in real Chromium for pieces with real behavior: the value tree keeping expansion across a stop, changed marks, the gutter, URL to focus and back, key handling. Virtual lists and CodeMirror need real layout, so not jsdom.

vitest · seconds
End to end

A handful of Playwright workflows against a real uscope web: launch, break, step, inspect; open a copied link in a second browser and see the same stop; reload and keep the focus; a viewer cannot continue.

Order of work

Phases

  1. Skeleton

    Flake tooling; web/ with Vite, React, TypeScript, Biome, Vitest, Playwright; embedded assets; uscope web with a program, --attach, or --core; tokens, roles, Host and Origin checks; hello and state; a page showing the session live in two tabs; recipes and the screenshot tool.

  2. Run and see

    Run control, threads, call stack, source with the gutter, breakpoints with conditions, hit counts, and logpoints, program output and input, the URL scheme and copy link, presence and notices, keys, the main layout.

  3. Inspect

    Scopes, the value tree with views and paging, watches in the URL, changed values, hover and inline values, editing values, the console with completion.

  4. Low level

    Disassembly, memory, registers, watchpoints, signal policy, modules.

  5. Polish

    Command palette, stop history, out-of-date link banners, themes, key help, speed on large programs.

Not yet

Limits

  • One program per uscope web. The debugger reaps every child of its process, so two debuggers cannot share one. Debug two programs with two servers.
  • No fork following. DAP follows forks by asking the editor to start another session; the web equivalent needs a second server per child.
  • No accounts or internet exposure. Sharing assumes a shared machine or a tunnel.
  • No recording. A link to a past stop can show where it was, but not its values. Saving a stop as a core dump would make links that last; that is a later idea.
