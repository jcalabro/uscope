uscope plan

Where the time goes, without changing it

uscope already knows what a debugger has to know to profile well: every module's addresses, call-frame information, inline chains, and how Go and tokio run tasks. This plan adds a sampling profiler that runs out of process on the kernel's perf events, an instrumented profiler fed by a small Rust SDK, one capture model and file both share, and web views built for interrogating them quickly. Production use is the default setting rather than an add-on: nothing heavy runs in the target, every loss is counted, and every stack uscope cannot trust says so.

  • Sampling uses perf_event_open from outside the target. It never uses ptrace and never runs code in the target. The kernel takes frame-pointer callchains in the sampling interrupt. uscope checks every frame against its own call-frame information, and repairs or extends a chain from a copy of the top of the stack where frame pointers are missing. The kernel's newer deferred callchains are an option, not the default: measured here, they cut Go stacks short at systemstack where the interrupt-time walk crosses correctly.
  • Async runtimes are first class. The static code roles uscope already assigns (Dispatch, RuntimeInternal, StackSwitch, Wrapper) cut every sampled stack into the scheduler's part and the task's part. Goroutines and tokio tasks then show as their own stacks of calls and awaits. Task snapshots, built on the existing runtime models and future walker, add profiles of where tasks wait.
  • Instrumentation comes from a no_std Rust SDK. Its sites are static records in an ELF section that uscope reads from the binary, and each site has its own enable byte. Events are 16-byte records stamped with raw TSC in per-thread rings. The program never sends a string, opens a socket, starts a thread, takes a lock, or blocks.
  • One capture model. Samples, zones, labels, and task states are columns over interned dictionaries: strings, modules, frames, and a stack prefix tree. They are sealed in self-contained chunks with the same container uscope's debug images use. Exports are pprof, folded stacks, and Chrome trace JSON; imports are pprof and folded stacks.
  • One query engine, pure and on the server, feeds the CLI, the web page, and the exporters. It provides time ranges, threads, tasks, labels, an ordered stack of transforms, diffs, and level-of-detail timelines. The page draws columns it receives on a canvas.
  • Testing: exact stack oracles from breakpoint events, naive oracles for every aggregation, lifecycle scenarios, fuzzed decoders and files, Vitest and Playwright for the views, and a simulator model of perf sampling whose shadow call stack is ground truth.
Goals

What we are building, and what we are not

G1

Fidelity the user controls

Three presets cover the range from production to analysis. prod samples at 49 Hz with frame-pointer stacks and enables only the instrumentation sites you name. dev samples at 999 Hz with copied stacks and every site enabled. max samples at up to the kernel's limit. Each knob can also be set alone: event, rate, stack mode and size, off-CPU, sites, window, symbols. The capture records which settings produced it.

G2

Safe in production

Nothing runs in the target to take a sample. The SDK never blocks and its memory is bounded. A controller holds uscope's own CPU and memory to a budget, lowering the rate when it must and recording that it did. If uscope dies, the target carries on unaffected.

G3

Fast to interrogate

One command records, and the web page opens on a flame graph. Views: timeline, call tree, sandwich, source annotation, diff, zone histograms. The URL holds every filter and transform. Interactions stay under 16 ms because the server sends pre-aggregated columns.

G4

Async stacks that read like code

A goroutine's or a tokio task's samples read as that task's stack of calls and awaits, under the task that runs them, with the scheduler's frames set aside. Where tasks wait is a profile in its own right.

G5

Captures as files

A capture is one self-describing file that loads offline on another machine with its symbols. It also exports to the formats the rest of the world reads.

G6

Honest results

A truncated stack, a lost sample, a throttled interval, a zone without its end, a task that changed while being read: each one is data the views show, never a guess.

Not in scope now. A fleet database, a hosted service, eBPF unwinders, allocation profiling, hardware tracing, and SDKs other than Rust. Deferred lists each with the condition that would bring it in. The capture model and the SDK's ABI are designed so none of them needs a redesign.

Pyroscope

Very little setup, diffs normalized to share of total, and a tag explorer that needs no query language.

L4

Parca, Elastic, OTel

Frames are recorded as (file identity, offset) and symbolized later, elsewhere. CFI is flattened once per binary into sorted rows. Overhead is held to a stated budget.

Take: (image, address) frames keyed by build id and content; lazy symbolization through the existing image cache; a stated overhead budget.

Avoid: 19 Hz as the only fidelity. Our rate is a knob, and the cost of turning it up is measured.

L5

Firefox Profiler and samply

Structure-of-arrays tables and a prefix-tree stack table, so each sample stores one integer. An ordered stack of transforms is serialized in the URL. Selections are stored as function paths, so they survive symbolization.

Take: the stack table, the transform stack and its short URL keys, call nodes in DFS order with subtreeRangeEnd.

L6

Go flight recorder and magic-trace

Always-on bounded rings of self-contained generations, dumped when a trigger fires: a slow request, a symbol hit.

Take: chunked self-contained captures and a rolling window. Triggers can be a breakpoint, a stop, an SDK call, a slow zone, or a button. A debugger has the best triggers of all.

L7

py-spy, Strobelight

Read runtime state from outside the process using known layouts, and make the choice between consistency and intrusion explicit.

Take: task snapshots read with DWARF layouts uscope already has; stop-the-world versus validated stopless reads as an explicit choice.

L8

pprof-rs, Pixie

pprof-rs unwinds inside a signal handler and has deadlocked in production on an allocator lock. Pixie's agent estimated 0.1% and measured 1.3%, because the user-space pipeline cost more than the samples did.

Avoid: any unwinding in the target, and any overhead claim not measured end to end, including uscope's own pipeline.

L9

speedscope, Superluminal, hotspot

The sandwich view; wake-up arrows from a wait to its waker; flame graphs that mark inlined frames; time-ordered and aggregated views kept apart.

Take: sandwich first; never mix "x is time" with "x is share" in one view.

Architecture

One pipeline, three sources, one model

Profiling reuses the debugger's architecture rather than standing beside it. A Recorder owns collection and is driven through a RecorderHandle. That handle works like DebuggerHandle: bounded request channels, acknowledged requests, events with a revision, and immutable snapshots. The Linux specifics stay at the edge. Everything after decoding is platform-neutral and reads ModuleImages through the image cache.

Threads and processes

  • No ptrace in a recording. uscope record -- PROG launches the program with enable_on_exec events, without tracing it, so Go's SIGURG and every other signal reach the program unobserved. --pid opens events on running threads. Ptrace is used only for an explicitly requested stop-the-world task snapshot (A3) and inside a debugging session.
  • Inside a debugging session, the controller thread still owns ptrace. The recorder runs beside it on its own threads and shares the controller's module list through events, never its state. The ptrace-only rules in AGENTS.md hold because no recorder thread calls ptrace.
  • All-stop holds. A debugger stop simply produces no samples (stopped threads do not run), and the stop is drawn on the timeline as a marker. "Profile until the next stop" and "the window before this stop" are triggers.

Sampling

Every stack confirmed or marked

Events

  • Launch opens, for each CPU, an event with pid=child, cpu=c, inherit=1, enable_on_exec=1 before the child execs. The child waits on a pipe until the events exist. New threads and processes are then followed with no race. Attach opens pid=tid, cpu=c, inherit=1 for each existing thread, redirected with PERF_EVENT_IOC_SET_OUTPUT into the per-CPU rings, which is what perf record -p does. The kernel allows sharing a ring across tasks only for per-CPU events. The measurements confirm the other half of that rule: per-thread events of different tasks cannot share one. File descriptors cost threads × CPUs; past a budget (default 16384) the attach refuses with the count rather than sampling a subset silently.
  • Event choice: cycles:u when the PMU opens, else task-clock. Frequency mode, with PERF_SAMPLE_PERIOD so each sample's weight is the period the kernel actually used. Default rates are 49 Hz (prod) and 999 Hz (dev), odd so they don't run in lockstep with periodic work. Hardware event choices (cache misses, branch misses, IBS) are a later knob over the same path.
  • Sample fields: IP | TID | TIME | PERIOD | CALLCHAIN | REGS_USER, plus STACK_USER of 512 B in prod and 16 KiB in dev. exclude_kernel and exclude_callchain_kernel are always set unless the caller holds CAP_PERFMON and asks for kernel stacks. defer_callchain is probed and recorded but off by default. It faults in non-resident stack pages, but here it cut 15.5% of Go samples short at systemstack, which the interrupt-time walk crosses. P3 decides from the exact-stack suite, per runtime, whether it ever becomes the default.
  • Side band goes on one dummy event per CPU: mmap2, build_id, comm, comm_exec, task, context_switch, sample_id_all.

The unwinding cascade

uscope cannot trust a frame-pointer chain blindly, and does not need to: it holds the CFI for every module. Each sample goes through these steps, and each one records its outcome:

  1. Leaf repair. Unwind the innermost frames from REGS_USER plus the copied stack top with UnwindInfo::unwind, through a MemoryReader over the copy and the module's file bytes. This fixes the caller that a frame-pointer walk skips in prologues, epilogues, and leaf functions without frame pointers. With 512 bytes it typically covers one to three frames.
  2. Confirm the chain. The kernel's frame-pointer return addresses, deferred or not, are accepted one at a time, but only while the CFI at each return address says its function keeps CFA = rbp + 16 with the saved rbp at CFA − 16. That is the definition of a valid frame-pointer frame. For Go, the same test uses pclntab's frame sizes, because Go's CFI does not describe its frame pointer. This rule is what catches the measured failure: a function without frame pointers between two that have them makes the chain skip it and still look complete. The CFI unwind from step 1 is spliced in where its (return address, CFA) matches a chain entry exactly.
  3. Extend from the copy. Where the chain breaks, at a function without frame pointers, the CFI unwinder continues through the copied stack (hybrid mode, 16 KiB in dev). It splices back onto the kernel chain at the next exact match.
  4. Runtime crossings. At a StackSwitch frame (Go's systemstack, mcall, cgo callbacks), unwinding continues only where the chain or the copy proves the crossing; the async section has the details.
  5. Mark the end. A stack ends at an Outermost frame (complete), or in a typed terminal frame: no unwind info, frame pointer not kept in <module>, stack copy exhausted, unmapped return address, depth limit. Terminal frames are ordinary frames in the tree, so a flame graph shows how much time ended in each and why.

Auto mode picks the cheapest mode that is correct for the target. At load, each image is classified by the fraction of functions that keep frame pointers past the prologue: from CFI for C, C++, and Rust, and from pclntab for Go. libstdc++ (3%), libgcc_s (6%), and tokio built without -C force-frame-pointers (1–3%) are typical images that force the copy. If every executable mapping keeps them, the copy stays at 512 B. Otherwise it grows to the hybrid size, and the capture records the image that forced it.

Off-CPU and wall clock

  • Unprivileged: SWITCH records give exact off-CPU intervals and preemption per thread. The timeline draws them, and per-thread "running %" comes from them. They carry no stack, and uscope does not guess one.
  • With CAP_PERFMON: a context-switch software event with user callchains gives off-CPU stacks, weighted by blocked time, with a threshold (default 1 ms) to bound cost.
  • Async programs mostly block in the scheduler, so thread off-CPU stacks say little. Task-wait profiles (A3) answer the real question.

Budget

A pure reducer, budget::step(state, observation) → actions, runs once a second. It reads uscope's own CPU (getrusage), bytes copied, samples, losses, and throttles. It lowers the rate or the stack size, or disables the hottest instrumentation sites, until uscope is under budget. Defaults: prod 1% of one core and 64 MiB; dev unbounded with a warning. Every action is a row in the capture, so weights stay correct and the views can show "rate lowered at 12.4 s". The reducer is unit-tested over recorded observation sequences.

Async runtimes

Goroutines and tasks as their own stacks

A thread running an async runtime switches between tasks thousands of times a second. Its native stack is a sandwich: the runtime's scheduler at the bottom, one task's frames above it, and runtime machinery mixed in. A profile that shows those stacks raw buries every task under the same scheduler frames. It cannot say which task, or which await, the time belongs to. uscope already solves this for the debugger with three static facts and two dynamic models. The profiler reuses all of them.

  • Code roles (src/debug_info/roles.rs), assigned once at load, are stored per frame in the capture:
    • Dispatch is where the runtime hands the thread to a task.
    • RuntimeInternal is scheduler and driver machinery.
    • Wrapper covers forwarding glue such as Pin, Box, into_future, and Go's autogenerated code.
    • StackSwitch marks frames that continue on another stack, and Outermost marks a stack's true end.
  • Coroutine facts: each async fn's resume function knows its CoroutineInfo, so a sampled frame inside handle::{{closure}} is shown as the async fn handle, at the line it is running.
  • Runtime models (src/runtime_model/{go,tokio}), pure behind RuntimeStop, list tasks, say what each thread runs, and give a parked task's registers. The future walker (futures.rs), also pure, follows a suspended future's __awaitee chain.

A1

Logical stacks from roles alone

This needs no memory reads, so it works on production captures. Splitting a stack at its innermost Dispatch frame gives the scheduler segment and the task segment. The task segment is re-rooted under a task-root frame keyed by its first non-runtime frame: the spawned future's type for tokio (from Harness<T, S>::poll's T), and the goroutine's entry function above goexit for Go. Wrapper frames fold away, and coroutine resume frames render as awaits. Samples with no Dispatch frame become [tokio worker], [go scheduler], or [idle] by role. This is a transform over the stack tree, so "raw native stacks" is one toggle away and the capture is unchanged.

It needs the scheduler and poll frames to be in the stack. A tokio build with frame pointers gives all of them in the interrupt-time walk (depth 18, measured). One without them needs the hybrid copy, or ends in a typed truncation in prod. docs/profiling.md recommends -C force-frame-pointers=yes for async Rust in production.

A2

Crossings proven, not guessed

Go switches stacks for runtime work. A sample on g0 joins the goroutine's frames only when the kernel's chain or the copy actually reaches them through systemstack's saved frame, with each step confirmed by Go's pclntab. Measured here, the interrupt-time walk does cross: 99.4% of Go samples end at goexit, including 634 that ran on the system stack, and mcall chains rightly end at mcall. When neither does, the stack ends in [system stack: goroutine frames not captured]. The goroutine is still attributed when A4 knows it. cgo transitions and signal frames use the existing TrapEntry and SignalTrampoline roles.

A3

Where tasks wait

Suspended tasks do not run, so CPU samples never see them. A task snapshot lists every task through RuntimeModel::tasks, with a parked goroutine's stack from task_context or a tokio task's await chain from the future walker. Each entry is weighted by the interval since the last snapshot, which gives a time-weighted "goroutine profile" and an await flame graph for tokio. Snapshots run at 1–10 Hz and are consistent: uscope pauses the process with the existing attach path, reads, and detaches, then records the pause it caused. A validated stopless mode (A5) comes later for production.

A4

Which task, by identity

A1 groups samples by kind of task. Telling individual tasks apart needs one more fact.

  • Go: R14 holds g in ABIInternal code, and REGS_USER carries it. Task snapshots map g pointers to goids and pprof labels (g.labels, already read for goroutine names). A sample gets a goid only when the snapshots before and after it agree on that g.
  • tokio: the SDK's optional hook records task polls as intervals (task id, spawn place), using tokio's task-poll hooks. These join samples by thread and time, exactly as labels do.

Without either source, task is NONE with its reason.

A5

Stopless snapshots

For production, snapshots read runtime structures with process_vm_readv while the program runs. Each task is read twice, comparing state, saved registers, and generation (goroutine status and sched; tokio header state and the future's discriminant). An entry that changed is discarded and counted, so a snapshot is consistent per task, not across tasks, and the view says so. Phase P8.

A6

Views

Task becomes a filter and a grouping like thread, and the URL can hold either. The timeline can show a lane per task (the tokio task-poll intervals, or goroutines when sampled with identity) or per worker thread. Await chains get their own flame graph, "where tasks wait", next to "where threads run".

This reuses the debugger's runtime knowledge directly: the profiler adds no Go- or tokio-specific code outside src/runtime_model and src/debug_info/roles.rs. A runtime added to the debugger later (another async executor, a green-thread library) gains profiler support through the same roles and model. Whatever the roles or models cannot prove stays a raw native stack with its reason.
Instrumentation

Tracy's fidelity without Tracy's footprint

Tracy's cost comes from what surrounds its zones, not from the zones themselves. It buffers events without bound until a viewer connects. It runs a profiler thread and LZ4 inside the target, takes a mutex for lock and allocation events, captures stacks synchronously, and opens a socket. The design below keeps only the hot path, makes it smaller, and moves everything else into uscope.

  • Sites are static data. Each zone! expands to a 32-byte record in a read-only uscope_sites section. It holds the name, file, line, kind, and flags, and refers to its strings and its state byte by self-relative offsets, so it needs no relocations. uscope reads the table from the binary at load into a new image table. The program never sends a name.
  • The off switch is one byte per site, in .bss: zero means off. uscope writes it with process_vm_writev, so enabling a site needs no stop and no cooperation from the program. A site whose feature is compiled out expands to nothing.
  • The on path is: read the state byte, branch, read the thread-local ring pointer, rdtsc, store one 16-byte record, store the head. No call, no atomic read-modify-write, no fence beyond x86's ordering.
  • Rings live in the program's own memory. Each is a per-thread, fixed-size, power-of-two ring that a thread maps once, on its first enabled event, through a cold path. A registry in the SDK's control block lists the rings. uscope reads each ring's head and records with process_vm_readv on its own schedule: every 10–50 ms while streaming, or only when a trigger fires in window mode. No fd is passed, no shared mapping exists, and nothing breaks if uscope dies.
  • The writer never waits. It overwrites the oldest records. The reader detects overwrites by position: after copying positions [t, h₀) it re-reads the head h₁ and discards every position below h₁ − capacity + 1, which the writer may have reused during the copy. Discarded and skipped positions are counted. One protocol serves both streaming and flight-recorder windows.
  • Zones are checked. An end record carries its site. The reader keeps a per-thread open stack and records any mismatch, missing begin, or missing end as a flagged zone, never as a silently repaired one.

Clocks

The SDK stores raw TSC when the TSC is invariant (CPUID 0x80000007 EDX bit 8) and the kernel's clocksource is tsc. Otherwise it stores vDSO CLOCK_MONOTONIC and says so in the control block. uscope converts TSC with the perf mmap page's time_zero, time_mult, time_shift, the kernel's own exact conversion to the perf clock that sample timestamps use. Zones and samples therefore share one timeline with no calibration loop. When the SDK falls back to MONOTONIC, the perf events use use_clockid = CLOCK_MONOTONIC instead. Periodic clock triples anchor the timeline to wall time.

Failure modes

  • uscope dies: rings keep overwriting, at the same per-event cost. The collector writes a generation word every second, and the SDK switches every site off when the word goes stale for ten seconds, so a dead collector costs one load and branch per site again.
  • fork: an atfork child handler disables the instance and clears the child's registry. A collector that follows the child (it sees FORK) re-enables it there. vfork children never record.
  • Signals: a thread-local "writing" flag drops and counts any event raised by a handler that interrupted a write. That is rare, explicit, and lock-free.
  • Thread exit: a TLS destructor marks the ring retired. The collector drains it and marks it free, and new threads reuse free rings, so thread churn never grows memory past the peak thread count × ring size (default 64 KiB, set by the collector before threads register).
  • Hostile or corrupt rings: the reader validates every header, record, kind, and length. A target can make its own capture wrong, flagged as such, but cannot crash or stall uscope.

What instrumentation adds to sampling

  • Zones, frames, plots, and messages as timeline tracks, plus Find Zone histograms with percentiles.
  • Labels are intervals too. A sample joins the zones and labels open on its thread at its time in one linear merge of two time-sorted columns. That gives Tracy's ghost-zone view and pprof's labels from one mechanism.
  • Triggers (trigger!("slow request")) seal the window around them.

Analysis

A pure query engine over columns

src/analysis is pure in the same sense as src/eval and src/runtime_model. It reads a merged capture and a query and returns columns. A boundary test keeps process control, I/O, clocks, threads, and debug-info loading out of it. Every view and exporter goes through it, so the CLI's uscope report, the web page, and the pprof exporter can never disagree.

A query

Query {
    capture, kind: Cpu | OffCpu | TaskWait | Zones,
    range: [t0, t1), threads, tasks, labels: [(key, value-set)],
    transforms: [Focus(path) | FocusFunction(f) | Merge(f) | Drop(f)
                 | CollapseModule(m) | CollapseRecursion(f) | Logical(on/off)],
    granularity: Function | Line | Address,   inlines: bool,
    diff_base: Option<Query>,
}

Aggregation in four linear passes

  1. Select each thread's samples in range with two binary searches. Apply label and task filters with a merge over the interval columns. Accumulate self[stack] into a reused dense array.
  2. Map stacks to call nodes under the transform stack and granularity. The map is memoized per stack node, so each tree node is visited once. Dropped stacks map to NONE. Logical async stacks (A1) are this step's default transform.
  3. Total with one reverse pass in topological order (total[parent] += total[child]). Function-level cum counts a function once per sample, as pprof does, using a per-stack "already counted" bit computed once per stack node.
  4. Lay out call nodes in DFS order with subtree_end. Flame graphs, tree expansion, and focus then become range operations. A diff runs steps 1–3 twice over one call-node table and returns two weight columns, normalized by default, and the view says so.

Cost is O(samples in range + stack nodes). Results are cached by (capture revision, query hash). A sealed capture never changes, so an answer for it is cached for good. A live capture's revision is its sealed-chunk count.

Timelines

Zones and task polls are per-thread, per-depth sorted arrays. A timeline request names a window and a power-of-two resolution. For each depth, the engine finds the first visible zone with a binary search, folds every run of zones narrower than 3 px into one rectangle with a count, as Tracy does, and recurses only into zones wide enough to see. Responses pad one window width on each side, as Perfetto's buffered bounds do, so panning rarely asks again. Sample density, counters, and off-CPU intervals use the same buckets with min, max, and last values.

Zone statistics

Find Zone keeps one sorted duration array per site, built lazily. It gives count, mean, median, P90/P99/P99.9, and a histogram on log or linear axes. Brushing the histogram filters instances and highlights them on the timeline. Self time is the duration minus the children's, computed once.

Interrogate, don't scroll

Views, in the order they ship

  1. Flame and icicle graph, from the same call-node table as the call tree, which has an invert toggle. Colors hash on module or package, so they stay stable across views, captures, and diffs. Production

Guarantees, not intentions

S1

The target

  • Sampling runs no code in it: no signals, no ptrace stops, no injected library.
  • The SDK, enabled, never blocks, locks, allocates on the hot path, or makes a system call after a thread's first event. Its memory is bounded by peak threads × ring size.
  • Disabled, a site costs one load and a branch; compiled out, nothing.
  • A dead collector is detected and the SDK goes quiet.
S2

uscope itself

  • A budget controller holds its CPU and memory, lowering rate, stack size, or sites in that order, and records each action.
  • Ring and window sizes are fixed at start.
  • It can run at SCHED_IDLE and inside a memory-capped scope.
  • A slow consumer drops data at the kernel's ring (LOST) or the SDK's (overwrite) and counts it. It never stalls the program.
S3

Privileges, smallest first

  • A launched child or your own processes: no privilege.
  • Other users' processes and SDK rings: CAP_SYS_PTRACE for process_vm_readv; perf alone needs read access, which Yama does not block.
  • Kernel stacks, off-CPU stacks, whole host: CAP_PERFMON.
  • uscope never asks for CAP_SYS_ADMIN.
S4

Containers and hosts

  • Files are opened through /proc/PID/root, and modules are identified by build id.
  • Deleted binaries resolve through /proc/PID/exe or are hashed while mapped.
  • --symbols=later keeps debug info off the host.
  • A capture records the seccomp or paranoid reason a feature was unavailable.
S5

Continuous mode

uscope record --continuous DIR --keep 24h writes rolling sealed chunk files and deletes the oldest. The web page opens the directory as one capture over time. The rolling window can trigger: on an SDK trigger, a slow zone, SIGUSR2, or a web button, it writes the last W seconds at full fidelity. There is no database; exporting pprof per chunk feeds Pyroscope or Parca when a fleet store is wanted.

S6

Overhead is measured, end to end

A bench recipe runs reference workloads (CPU-bound C, the Go server fixture, a tokio server fixture, an instrumented Rust fixture) under each preset. It reports target throughput and latency change and uscope's own CPU and memory, against a baseline file like bench/baseline.json. The prod preset's budget, under 1% of target throughput, is a checked number, not a claim.

Testing

Oracles for every layer

A profiler's output is statistical, but most of its correctness is not. Whether a stack is right, a record decodes, a zone nests, or an aggregate sums can each be checked exactly. The plan puts each check where it is exact and cheap. Statistics are left to the few properties that really are statistical, asserted with bounds that cannot fail by chance.

Exact stacks

The key oracle. A test-only event source opens an execute-breakpoint perf event (HW_BREAKPOINT_X, sample_period=1) on a chosen instruction. Every execution is one sample through the real pipeline, so the fixture's known call path is asserted exactly. This runs over GCC and Clang, O0 and O2, PIE and non-PIE, with and without frame pointers, Rust, Go, and tokio. Builds without frame pointers must produce either the right stack or a typed truncation, never a wrong caller. The first test written is the measured failure: a Rust build without frame pointers, whose plain walk jumps from the leaf to main.

nextest · seconds
Differential unwind

For the same registers and stack bytes, the sample unwinder and the debugger's stop unwinder (ptrace, at the same PC) must agree frame for frame. The debugger is the reference.

nextest
Valid-stack property

Fixtures with a statically known call graph (hot-calls.c-style, plus Go and tokio) are sampled at high rate. Every sampled stack must be a path in that graph or end in a typed truncation. Work ratios of 1:4:16 must come out in that order with ≥ 2 000 samples, a bound whose chance failure is far below one in a billion.

nextest · ~1 s each
Pure units

Kept to where logic is intricate. Record decoders (wraparound, LOST, THROTTLE, deferred-cookie stitching, MMAP2 build ids), the ring reader's overwrite rule, the FP confirmation and splice, logical async splitting, the budget reducer, and TSC conversion.

cargo test · ms
Naive oracles

Proptest generates random captures, then compares every aggregation, transform, inverted tree, diff, timeline fold, and percentile against a slow, obviously correct implementation over the same data.

proptest · seconds
Fuzzing

Perf record streams, SDK rings, .usprof chunks, and pprof and folded imports must never panic, always end, and fail with a typed error. The harnesses reuse the image fuzz targets' structure.

just fuzz · contained
Lifecycle scenarios

A support::Recording harness, in the shape of Scenario, drives the public RecorderHandle path with deadlines and a transcript, and verifies nothing survives. Cases: launch, and attach to ExternalProcess; target exits, crashes, or is killed mid-capture; thread churn, fork, and exec; uscope killed mid-capture, after which the SDK fixture must finish normally; cancellation, budget actions, and triggers. Each waits only for what it can observe: a line the fixture prints, a record, or a /proc fact.

nextest · just stress
SDK behavior

An instrumented fixture emits a known zone tree, label set, and plot series, and the capture must match exactly. Tiny rings must give exact, counted losses. A signal-handler fixture checks the in-signal drop. A golden C program writes the ABI by hand. Miri covers the SDK's pure parts.

nextest
Async

Breakpoint events inside known async fns give exact logical stacks: task root, then awaits, then leaf, on tokio 1.52 and current, at o0 and o3. Go leaves on the system stack must cross correctly or truncate typed. Task snapshots of the tokio and Go fixtures that park tasks at known awaits must list exactly those chains. These reuse the oracles of plans/tokio.md and plans/go.md.

nextest
CLI and interop

uscope report rendering, flags, and batch behavior are tested separately, as CLI tests are today. Exported pprof is read back by our importer and by the Nix toolchain's go tool pprof -raw, and the totals must agree.

nextest
Simulator

The simulated kernel gains perf sampling. A sample fires at a Choices-drawn retired-instruction count, with IP, registers, a peek_bytes stack copy, and a frame-pointer callchain, all pinned by dual-run conformance rules (K-PERF-*). The shadow call stack is ground truth: every unwound sample must equal it or end in a typed truncation. The ring reader runs against a golden program writing the ABI, at adversarial interleavings, so the torn-read rule is tested exactly. New oracles come with sabotage tests and coverage marks.

just sim
Web

Vitest covers column decoding, layout and fold geometry, hit testing, URL round trips of every view state, and transcript replay from recorded scenarios. Playwright, in Chromium and Firefox, opens real fixture captures. The flows tested: record from the page; select a range, then focus, then diff; Find Zone; source annotation; and a shared link that reopens the same view. web-probe takes screenshots.

just web-test · web-e2e
Overhead and size

Not in the gate, because it is noisy. just profile-overhead measures each preset against baselines. Deterministic counts, such as allocations per sample and bytes per sample in the file, go in bench-smoke.

bench · minutes
Each new test is written before its fix and watched to fail. Fixtures are built by just build-test-programs and never by tests. Every run is memory-capped. The added fixtures are few and small, measured against the cold fixture build and the just gate, because fast loops are a requirement.

Open questions

For you to decide

Q1

What the Rust SDK covers

The request says "a Rust SDK for doing sampling profiling". Sampling needs no SDK, so this plan reads it as the program-side SDK: zones, labels, frames, plots, triggers, and optionally task-poll hooks, all of which also enrich samples. If you meant an in-process sampler library, like pprof-rs, the plan would need a different SDK. D1 argues against one.

Q2

Default rates

49 Hz for prod and 999 Hz for dev are proposals. On this machine they cost under 0.1% and about 0.4%. Is 49 Hz enough fidelity for production, or should it be 99 Hz (≈0.15%)? The reference workloads in P8 settle it for real.

Q3

Stop-the-world task snapshots

Are they acceptable in dev before the stopless mode exists, or should waits wait for P8?
